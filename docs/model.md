# Описание имитационной модели

[Первичные артефакты](../README.md)

## Правила обработки

1. Движок извлекает ближайшее событие календаря и устанавливает модельное время `now`. Событие `ARRIVAL` имитирует действие пользователя. Отдельного периодического сканирования запросов обработчиком нет.
2. Источник создаёт заявку, а диспетчер постановки помещает её в буфер. Он имеет ссылку на буфер и не обращается к приборам. Даже при свободном приборе заявка сначала ставится в буфер и затем может быть выбрана при том же `now`.
3. Если свободного места нет, диспетчер удаляет самую старую ожидающую заявку и вставляет новую в освободившуюся ячейку. Отказ относится к источнику удалённой заявки. Обслуживаемые заявки не прерываются. Ячейки буфера после удаления не сдвигаются.
4. После поступления или завершения обслуживания движок вызывает диспетчер выбора. При отсутствии незавершённого пакета и наличии свободного прибора выбирается источник с минимальным номером среди представленных в буфере. Непосредственно перед выбором первой заявки фиксируются ID всех его ожидающих заявок.
5. Все приборы обслуживают только текущий пакет. Новые заявки не дополняют его, даже если пришли от того же источника. Внутри пакета используется порядок `(createdAt, id)`.
6. Свободный прибор ищется циклически от `workerPointer`. Только успешное назначение передвигает указатель на позицию после выбранного прибора. Если назначения нет, указатель сохраняется.
7. При назначении заявка удаляется из буфера, переносится из `waitingIds` в `inServiceIds`, начинается обслуживание и планируется `COMPLETION`.
8. Завершённая заявка удаляется из `inServiceIds`. Выбитая ожидающая заявка удаляется из `waitingIds`, если принадлежала текущему пакету. Пакет считается завершённым, когда оба множества пусты. Исходный снимок `initialIds` сохраняется для отображения.
9. Если в текущем пакете больше нет ожидающих заявок, но остаются обслуживаемые, свободные приборы простаивают. Следующий пакет начинается только после полного завершения текущего. При поступлении запроса в полностью простаивающую систему начальный пакет создаётся сразу.

### Принятые соглашения

- Источники имеют номера от 1 до N; меньший номер означает более высокий приоритет. Приоритет между пакетами не прерывает уже начатый пакет.
- Индексы приборов и ячеек буфера — от 0. Начальное значение `workerPointer` — 0.
- `RequestId` — пара `(sourceId, sequenceNumber)`. При одинаковом времени создания заявки сравниваются по этой паре лексикографически. Так разрешаются совпадения при выбивании и FIFO.
- Число источников N, приборов M и ёмкость буфера B задаются отдельно: N ≥ 1, M ≥ 1, B ≥ 1. Для каждого источника λᵢ > 0. Границы обслуживания удовлетворяют 0 < a < b. Генераторы случайных чисел имеют фиксируемые начальные значения для воспроизводимости.
- Генерация идёт до T включительно. События поступления после T не добавляются. Уже созданные заявки обслуживаются до опустошения системы. Время наблюдения `Tobs = max(T, время последнего события)` включает этот этап.
- API-вызовы и их ответы представлены длительностью обслуживания одной заявки. Лимит внешнего API, например 30 обращений/с, — характеристика бизнес-домена, отдельная от числа приборов. Эта базовая СМО не содержит сетевого клиента, дедупликации или механизма жёсткого ограничения RPS; её параметры сами по себе не гарантируют соблюдение квоты API. Отказ Д1ОО3 означает выбивание из буфера и не подменяет HTTP 429.

## Календарь и пошаговое состояние

Календарь хранит будущие `ARRIVAL` и `COMPLETION`. Порядок извлечения: `(time, typePriority, sequenceNumber)`. При одинаковом времени все завершения имеют приоритет перед поступлениями. События одного типа и времени обрабатываются в порядке добавления. После каждого извлечённого события выполняются все его мгновенные действия и сохраняется шаг.

| Поле строки календаря | Содержание |
|---|---|
| `time` | Модельное время события |
| `type` | ARRIVAL или COMPLETION |
| `sourceId` | Источник для ARRIVAL |
| `workerId` | Прибор для COMPLETION |
| `requestId` | Заявка для COMPLETION |
| `sequenceNumber` | Уникальный порядок добавления в календарь |

Мгновенные действия выполняются при текущем `now` и идут в журнал шага в фактическом порядке. Например, при переполнении: генерация → выбивание → постановка новой заявки → возможный выбор → начало обслуживания.

| Действие | Где фиксируется |
|---|---|
| GENERATED — заявка создана | `recordGenerated` |
| REJECTED — заявка выбита | `recordRejected` |
| BUFFERED — новая заявка помещена в буфер | `recordAction(BUFFERED, …)` |
| SELECTED — заявка выбрана из пакета и извлечена | `recordAction(SELECTED, …)` |
| STARTED — заявка назначена прибору | `recordStart` |
| COMPLETED — обслуживание завершено | `recordCompleted` |

Пошаговый снимок содержит время и обработанное событие, состояния источников, все ячейки буфера, исходный и оставшийся состав пакета, занятость каждого прибора, текущий `workerPointer`, счётчики и проценты отказов, таблицу будущих событий и журнал действий текущего шага.

## Сбор статистики

Для каждого источника фиксируются числа созданных Gᵢ, завершённых Cᵢ и выбитых Rᵢ заявок. Вероятность отказа оценивается как `Rᵢ / Gᵢ`. После завершения прогона с обслуживанием остатка `Gᵢ = Cᵢ + Rᵢ`.

Для завершённых заявок:

- ожидание: `W = serviceStartedAt − createdAt`;
- обслуживание: `S = completedAt − serviceStartedAt`;
- пребывание в системе: `V = completedAt − createdAt = W + S`.

В таблице ОР1 выводятся средние W, S, V и эмпирические дисперсии W и S. Дисперсия считается как сумма квадратов отклонений от среднего, делённая на число завершённых заявок. Выбитые заявки учитываются отдельно в Gᵢ и Rᵢ и не входят в выборку времён успешного обслуживания. При отсутствии наблюдений соответствующая величина отображается как «—».

Коэффициент использования прибора j: `Kⱼ = busyTimeⱼ / Tobs`. На промежуточном шаге в занятость включается уже прошедшая часть текущего обслуживания; к завершению прогона все интервалы обслуживания закрыты.

## Контрольный сценарий

Ручной пример для проверки последовательности действий: два прибора (0 и 1), две ячейки буфера, указатель 0, T = 2 с. Времена поступлений и обслуживания заданы для этого примера; длительности лежат в [0,5; 3] с. ID заявки записан как `источник.номер`.

| Время, с | Событие | Состояние после обработки |
|---|---|---|
| 0,05 | Поступает 1.1 | Начальный пакет {1.1}; прибор 0 занят до 1,00; указатель 1. HappyFlow. |
| 0,10 | Поступает 2.1 | Ячейка 0 = 2.1. Прибор 1 свободен, но пакет {1.1} ещё не завершён. |
| 0,20 | Поступает 2.2 | Ячейка 1 = 2.2. Буфер заполнен. |
| 1,00 | Завершается 1.1 | Фиксируется пакет {2.1, 2.2}. 2.1 → прибор 1 до 3,00; 2.2 → прибор 0 до 4,00. Буфер пуст, указатель 1. |
| 1,10 | Поступает 1.2 | Ячейка 0 = 1.2; оба прибора заняты. |
| 1,20 | Поступает 3.1 | Ячейка 1 = 3.1; буфер заполнен. |
| 1,30 | Поступает 1.3 | Старейшая 1.2 выбита, отказ источнику 1. Ячейка 0 = 1.3; приборы заняты. |
| 1,40 | Поступает 2.3 | Старейшая 3.1 выбита, отказ источнику 3. Ячейка 1 = 2.3. Заявка 2.3 не дополняет пакет {2.1, 2.2}. |
| 3,00 | Завершается 2.1 | Прибор 1 свободен, но ждёт завершения 2.2. Заявки 1.3 и 2.3 остаются в буфере. |
| 4,00 | Завершается 2.2 | Пакет завершён. По приоритету выбирается {1.3}; заявка → прибор 1 до 4,75; указатель 0. |
| 4,75 | Завершается 1.3 | Следующий пакет {2.3}; заявка → прибор 0 до 5,25; указатель 1. |
| 5,25 | Завершается 2.3 | Система пуста: создано 7 заявок, завершено 5, выбито 2. |

### Выбивание участника текущего пакета

Пусть B = 3, два прибора обслуживают 2.1 и 2.2, а 2.3 ожидает в составе того же зафиксированного пакета. Остальные ячейки заполнены более новыми заявками других источников. Если приходит ещё одна заявка, старейшая ожидающая 2.3 выбивается. Её ID удаляется из `waitingIds`; отказ записывается источнику 2. Пакет остаётся активным до завершения 2.1 и 2.2. Уже обслуживаемые заявки не затрагиваются.

## Структуры данных диаграммы классов

| Тип | Данные и назначение |
|---|---|
| `SearchParams` | Поисковая строка, категория, фильтры; содержимое запроса не меняет дисциплины СМО. |
| `SourceSnapshot` | Номер источника, λᵢ, последний порядковый номер заявки. |
| `RequestSnapshot` | ID, источник, параметры, статус и временные отметки заявки. |
| `BufferSnapshot` | Массив ячеек с `RequestSnapshot` либо пустыми значениями. |
| `WorkerSnapshot` | ID прибора, текущая заявка либо отсутствие заявки, планируемое завершение. |
| `WorkerPoolSnapshot` | Состояния приборов и `workerPointer`. |
| `BatchSnapshot` | Источник, `initialIds`, `waitingIds`, `inServiceIds`. |
| `ActiveService` | ID заявки, источник и время начала незавершённого обслуживания прибора. |
| `RunningMoments` | Число наблюдений, среднее и накопленная сумма квадратов отклонений. |
| `JournalEntry` | Время, порядковый номер действия в шаге, `ActionKind`, ID заявки и связанный прибор при наличии. |
| `ActionKind` | GENERATED, REJECTED, BUFFERED, SELECTED, STARTED, COMPLETED. |
| `StatisticsSnapshot` | Текущие счётчики, вероятности отказа, накопленные времена и загрузка на момент шага. |
| `StepSnapshot` | Время, обработанное событие, снимки всех компонентов, будущий календарь, журнал текущего шага. |
| `StatisticsReport` | Итоговая таблица ОР1 по источникам и приборам. |

`WorkerPool.start()` делегирует обслуживание конкретному `Worker.start()`, затем сдвигает указатель. `WorkerPool.finish()` делегирует завершение прибору и возвращает его заявку. `PlacementDispatcher.place()` возвращает выбитую заявку или `null`: движок фиксирует отказ и уведомляет диспетчер выбора. Методы `onEvicted()` и `onCompleted()` изменяют только соответствующие множества текущего пакета.
